# Project Architecture Guide

## Scope

Hextech Simulator is a single fullstack Next.js application. This document owns
technical organization and dependency boundaries. Product rules and contracts
belong in their dedicated documents.

```text
src/
  app/       Next.js routing, layouts, and thin route adapters
  features/  Product-facing UI and client workflows
  server/    Framework-free backend domains and persistence
  shared/    Generic components, utilities, and transport contracts
```

Do not create a separate frontend/backend project split unless explicitly
requested.

## Ownership

### `src/app`

Contains App Router entry points, layouts, loading/error boundaries, and thin
HTTP adapters. Pages compose feature UI and server reads; route handlers parse
and validate requests, establish context, call a server owner, and translate
results to HTTP responses. Do not put reusable rules or persistence logic here.

### `src/features`

Contains product UI and browser workflows organized by capability. Existing
features include `game-board`, `match-simulator`, `sideboarding`,
`online-matchmaking`, `card-catalog`, and `card-presentation`.

Feature code may contain components, hooks, view models, local reducers,
feature API adapters, and types. Keep feature-specific UI inside its feature.
Expose a narrow feature entry point when another feature needs a stable public
surface; otherwise avoid deep cross-feature imports.

### `src/server`

Contains backend code that must not run in the browser. It is organized by
backend domain, not by mandatory abstract layers:

```text
server/game/               match lifecycle, rules, timing, projections, combat
server/deck/               parsing and legality
server/card-catalog/       behavior definitions and canonical publication
server/catalog/            local set-data contracts and loading
server/online-matchmaking/ rooms and socket coordination
server/db/                 MongoDB connection and repository support
server/repositories/       focused persistence adapters
server/services/           focused application services
```

Keep server modules independent of React, Next.js, and feature UI. Use
repositories for persistence, policies for authorization, and services for
application coordination where those responsibilities are genuinely distinct.
Do not reorganize coherent server domains merely to force every file into a
generic layer.

### `src/shared`

Contains only generic reusable UI, utilities, and transport contracts. Before
moving code here, confirm that it is independent of a feature's domain language,
can be reused by unrelated features, and makes ownership clearer. Game-board,
match, deck, or card-specific UI belongs to its feature.

## Dependency direction

Keep entry points thin and direct work toward the responsible domain:

```text
route/page/client workflow
  -> feature or server boundary
    -> domain service/module
      -> policy/repository when needed
        -> persistence or external system
```

Server authority remains on the server: game legality, payment, rule execution,
hidden-information handling, persistence, and viewer projections must not be
reimplemented in React. The client renders projected state and submits intents.

Avoid circular dependencies. A feature should not reach into another feature's
internal component tree when that feature can expose an intentional public API.

## Components and client boundaries

Use one file per meaningful exported React component. Keep small private
subcomponents local until they gain independent responsibility, reuse, testing,
or client-only runtime needs. Do not split simple code solely to reduce line
count.

Components are Server Components by default. Add `"use client"` only for
browser APIs, state/effects, event handlers, drag-and-drop, or client form
state. Isolate interactive behavior into the smallest practical component.

For standard application controls, inspect the local shadcn-style primitives
first. Proprietary game-board, card, spatial, animation, and drag interactions
may be custom feature components.

## Naming and imports

- Use kebab-case for ordinary authored files.
- Preserve framework-required names such as `page.tsx`, `route.ts`, and dynamic
  segment names, plus generated/configuration/source-data names.
- Use PascalCase React components, camelCase variables/functions, and
  UPPER_CASE fixed constants.
- Use `@/` absolute imports across root or feature boundaries; use relative
  imports locally when clearer.

## Contracts, generated files, and tests

Keep durable transport, validation, and serialization contracts authoritative
and avoid parallel incompatible representations. Validate external and
persisted data through the project's schemas.

`data/catalog/mvp.json` and
`src/server/catalog/fixed-mvp-cards.generated.ts` are generated by
`scripts/build-mvp-card-catalog.ts`. Change inputs and regenerate them; use
`npm run catalog:check-mvp` to verify synchronization.

Tests currently live in `tests/**/*.test.ts` and run with Node plus `tsx`.
Prefer focused behavioral, contract, and regression tests over tests that freeze
temporary UI structure. Keep global tests while that runner convention remains;
do not relocate tests as incidental cleanup.

## Validation

Use package scripts rather than invented workflows. Run focused checks first,
then typecheck, lint, tests, and build as impact warrants. Manual validation is
required for interaction-heavy gameplay/UI behavior that automated checks do not
meaningfully prove.
